Architecture comparison

reactoscope vs. vectorsynthesis vs. xyscope.js vs. LaserBoy vs. laser-dac-rs vs. PlayzerX — how six systems turn geometry into a beam-position signal (and, for two of them, get it onto real hardware), and where they disagree.

Finding 1

LaserBoy and laser-dac-rs both close the corner-safety gap ADR-0008 said had no reference — and they disagree with each other on how.

Finding 2

reactoscope's ordering minimizes raw distance; LaserBoy minimizes physical settle-time cost. Same algorithm shape, different cost function.

Finding 3

Naming collision: LaserBoy's "Z channel" is a spatial depth axis. reactoscope's "Z channel" is analog intensity/blanking. Same letter, unrelated meaning.

Finding 4

laser-dac-rs generates zero points — it's the delivery layer reactoscope doesn't have yet, sitting downstream of everything else here.

Finding 5

laser-dac-rs's own "oscilloscope" backend solves reactoscope's namesake problem independently — and adds two anti-glitch behaviors reactoscope lacks.

Finding 6

PlayzerX is the only project driving a real, physical laser — a single resonant MEMS mirror, not dual galvos — and it has zero corner-safety logic of its own.

Where's laser-dac-rs?
Not in this table — it generates zero points. Its Frame/Stream API takes LaserPoints the caller already produced and is purely about pacing and delivering them. It's the layer reactoscope doesn't have yet: something downstream of buildCoordBuffer owning hardware timing, reconnect, and safety once points already exist. See the dedicated section below.

⚠ Naming collision

LaserBoy's CHANNEL_Z is a spatial position axis (3D depth). reactoscope's "Z channel" is an analog intensity/blanking control (−1 = blanked, +1 = full intensity). Same letter, two projects, two unrelated real-world axes each named itself after. Don't assume shared meaning when cross-referencing the two codebases.

Path generation — the real divergence

reactoscope and LaserBoy are the only two of the five that solve an ordering problem at all — both use a greedy nearest-candidate walk with optional reversal. laser-dac-rs doesn't order anything (that's the caller's job) but it does own what happens at the seam once ordering is done — a third, distinct answer to travel-safety.

reactoscope — distance-only cost

For each unvisited segment, compare raw Euclidean distance from the current beam position to that segment's start/end. Pick whichever is closest. No awareness of the turn angle needed to actually continue there.

LaserBoy — settle-time cost

points_away = dwell points for the incoming turn angle + interpolation steps for the blank jump + dwell points for the outgoing turn angle. Two candidates equidistant in pixels can cost very differently once the turn is priced in.

Why this matters
A smooth continuation and a sharp reversal, at equal distance, look identical to reactoscope's current cost function. LaserBoy's metric tells them apart — because on real hardware they aren't remotely equivalent in cost. LaserBoy also merges shared-endpoint segments before ordering (conglomerate_lit_segments), reducing segment count rather than just ordering what's there — reactoscope's collectSegments does the opposite by default, fracturing every polyline into 2-vertex pairs before ordering even starts.

Shape distinction

All six systems agree on one thing: "shape" is a build-time or edit-time concept that does not survive translation to a beam-position signal.

reactoscope

Shapes are THREE.Object3D instances — but orderSegments flattens everything into one undifferentiated pool.

vectorsynthesis

Named wavetable per shape, lost the instant the phasor sweeps past its window.

xyscope.js

this.shapes array exists at the p5 API level, collapsed by buildWaves().

LaserBoy

"Lit segments" are individually addressable (explode_segments) — but identity is gone the moment a frame is exported.

laser-dac-rs

Never sees shapes, only a flat point vector per Frame — but frame identity does survive to the seam: TransitionPlan knows which two frames are adjacent.

PlayzerX

No concept of shape or frame — only flat X/Y/color arrays passed to SendData*. Not even laser-dac-rs's frame-boundary survives here.

Corner-safety: the gap ADR-0008 flagged, now doubly closed

ADR-0008 said

"There's no existing pattern to crib from — this would be new design work, not integration of a known technique." Neither vectorsynthesis nor xyscope.js had a real corner/galvo-overshoot safety mechanism to point to.

LaserBoy's add_dwell classifies every vertex-to-vertex transition and inserts repeated copies of the vertex — more at sharper turns, none on a straight line:

0°
straight line
45°
90°
right angle
135°
180°
full reversal

dwell = ceil((angle / π) × sample_rate × max_dwell_microsec)

laser-dac-rs takes a different approach: fixed dwell duration regardless of angle, but a smooth quintic-eased transit whose point count scales with distance (see the comparison table above). Its dwell/transit only fires at frame seams — it has no visibility into corners inside a single submitted frame, which is exactly the case LaserBoy's add_dwell covers and laser-dac-rs doesn't.

A working extension point, not just a hypothetical
ADR-0008 named two possible homes for corner-safety logic: inside the resampler (buildCoordBuffer), or as a downstream DAC-adapter concern. laser-dac-rs picked the adapter side and shipped it as a real, documented API: OutputFilter runs on the exact point slice about to hit hardware, after transition composition — its own worked example clamps out-of-range points to blanked. This doesn't mean reactoscope must adopt the same placement, but it proves that placement is workable, not speculative.
PlayzerX has none of this — confirmed, not assumed

A grep for "order," "sort," "nearest," "blank," "dwell," "transition," or "interpolat" across PlayzerX's entire implementation returns zero matches. Of the two projects in this comparison that talk to real beam-steering hardware, laser-dac-rs chose to own seam-level safety; PlayzerX chose to own none of it. That's the clearest illustration anywhere in this comparison of how much LaserBoy's and laser-dac-rs's cost functions actually add over doing nothing at all.

Hardware delivery layer (laser-dac-rs only)

None of reactoscope, vectorsynthesis, xyscope.js, or LaserBoy model this layer at all — genuinely new territory, not a variant of something the other four already do differently. PlayzerX has the raw material (a real device FIFO — see its own section below) but none of the scheduling/safety logic on top; treat it as the floor this layer starts from, not a second full example of it.

Backend timing model

OutputModel unifies three real hardware pacing strategies behind one scheduler: UsbFrameSwap (Helios — wait for ready, write whole frames), NetworkFifo (Ether Dream/LaserCube/AVB — top up a queryable queue), UdpTimed (IDN — OS send time against a deadline is the only clock).

Color delay

Galvo mirrors settle slower than color modulators respond, so R/G/B/intensity are deliberately delayed 50–200µs relative to X/Y. A physical-latency concept none of the other five projects model at all — not even PlayzerX, whose onboard filter treats the whole drive signal generically.

Startup blanking

Forces the first points after arming to stay blank so mirrors reach their initial position first — same idea as LaserBoy's intro segment, arrived at independently.

Reconnect & liveness

Automatic reconnection with backoff, plus a read-only liveness handle for watchdogs. Hardware disconnection isn't a first-class case anywhere else here — PlayzerX has manual connect/disconnect but no automatic backoff-and-retry logic.

The closest existing code to reactoscope's own name
The oscilloscope backend drives a real scope tube's XY input from stereo audio — X→left, Y→right, no color channel at all, because a scope tube has none. It independently solved two anti-glitch problems reactoscope doesn't currently address: on underrun it holds the last output sample instead of snapping to center, and on mute it ramps toward center over ~3ms instead of cutting instantly. It also states the hard constraint that separates a scope from a laser DAC: the beam is always visible, there is no "off" — so blanked points must still carry real position data, or the beam visibly jumps. reactoscope's continuous Z-channel already gets this right by construction (blanking dims to −1, it never removes the X/Y sample) — good to know this was a real risk the design already avoids, not one it was never exposed to.

PlayzerX: a real MEMS-mirror laser projector, not a galvo

Every other project here targets, emulates, or abstracts over dual galvo mirror hardware — one moving-magnet/moving-coil galvo per axis, the traditional ILDA convention. PlayzerX targets something mechanically different: a single biaxial MEMS mirror chip that steers both X and Y from one micro-mechanical device. That changes what "corner safety" even means, and it's worth its own section rather than folding into the galvo-oriented ones above.

Thin API, zero built-in safety

Connection lifecycle + SendDataXY/XYM/XYRGB + buffer queries. That's the whole surface. No ordering, no transition composition, no output filter — the host must hand it an already-safe point stream.

Hardware-fixed data format

12-bit X/Y (4096 steps, origin at 2048), 8-bit color/modulation. XYM vs. XYRGB is which physical unit you bought, not a runtime choice.

Real circular FIFO, two independent rates

125,000 samples (mono) / 83,333 (RGB) onboard. Write rate (host→device, ≤~50,000/sec over USB serial) and read rate (device→mirror, SetSampleRate, default 22,000/sec) are fully decoupled — and fully manual to manage.

A zero-software analog mode exists too

PlayzerX-AIN drives the mirror from three raw voltage channels (X, Y, intensity) — "cannot be directly controlled via a software interface." Third-party laser-show controllers and even a bare NI-DAQ card drive it this way.

A failure mode with a name: mechanical resonance and ringing

PlayzerX's own docs warn plainly: the MEMS mirror is "a high-Q spring-mass system" — sending too few points at too high a sample rate produces sparse, jagged excursions that excite its resonance and ring. The fix shipped is an onboard low-pass filter on the controller, a hardware-level mitigation categorically different from every software fix elsewhere in this comparison (LaserBoy's angle-proportional dwell, laser-dac-rs's quintic-eased transit). Neither of those techniques exists here — the device compensates for its own physics instead of asking the point stream to be gentler.

Galvo response (LaserBoy / laser-dac-rs world)

Heavily-damped servo loop: settles smoothly onto target, at worst a small overshoot software dwell/easing can absorb.

MEMS mirror under sparse+fast drive

High-Q resonant structure: a rapid excursion can ring for several cycles before settling — a firmware-level LPF dampens it, not a software point-insertion algorithm.

Limitations

12-bit position resolution

4096 steps/axis — coarser than every other project's f32/16-bit-equivalent position handling.

No safety logic of any kind

Nothing here would catch the mechanical-ringing failure mode its own docs warn about — avoiding it is entirely on the caller's point-generation code.

Manual backpressure

Buffer-level management is the caller's job (polled GetSamplesRemaining, WaitForBufferLevel) — no OutputModel-style scheduler abstracting it away.

Spec inconsistency

The header's own doc comment says SetSampleRate ranges 200–50,000/sec; the USB protocol reference says 50–50,000. Verify against real hardware before depending on the exact floor.

Heavy, dated dependency footprint

Prebuilt Windows .lib/.dll artifacts; the underlying device layer bundles OpenCV 2.4.13 binaries (c. 2013) — the heaviest, oldest dependency chain in this comparison.

Points-per-second (kpps) budgeting

The one genuinely physical constraint in this whole comparison: a galvo mirror can only redirect the beam so many times a second. Real laser projectors run roughly 20–40 kpps typically, 60–100 kpps at the high end. Here's how each project treats that ceiling — or doesn't.

reactoscope has no kpps concept at all
Effective point rate is an emergent, unchecked product of two independent sliders: coordBufferSize (256–4096 points) × scanFrequency (0.1–192 Hz). That spans ~26 to ~786,000 points/sec — four orders of magnitude past real hardware, with nothing flagging it.

reactoscope's slider range vs. real laser hardware

Log scale. reactoscope's configurable range fully contains the real hardware band but extends roughly 8× past it in both directions with no warning.

vectorsynthesis

Audio sample rate is the point rate directly — no separate resample stage. vs-decimate.pd thins density manually; nothing computes the decimation a real DAC's kpps ceiling would require.

xyscope.js

Not applicable — never targets galvo hardware, so mechanical kpps isn't a constraint it needs to model.

LaserBoy

sample_rate is a first-class, rig-calibrated constant driving every dwell formula. still_frame_duration converts a kpps budget into an explicit repeat-count computation — but a too-complex frame just silently takes longer to draw once.

Two things nobody else here does
LaserCube Network doesn't trust a hardcoded spec number — it reads the actual connected unit's self-reported rate ceiling at runtime and clamps requests to it (resolved_point_rate_max, clamp_point_rate). And the pps_min field's own doc names the low-end failure mode too — too few points/sec "increases point dwell time and can produce flickery output." Every other project in this comparison only worries about too many points, never too few.

Enforcement is real but narrower than it first looks: bounds are checked in the reconnect path (rejecting a reconnect into a device that can't sustain the current rate — one test is literally named "PPS 500 is below pps_min=1000 — should be rejected even with reconnect"), but there's no equivalent hard rejection visible on the very first session-start call. And two backends (oscilloscope, avb) aren't native point-rate protocols at all — they're audio interfaces at a fixed sample rate, reconciled to an arbitrary requested pps via StreamingResampler.

PlayzerX: kpps from measured hardware behavior, not a spec field
Two independent rates, not one: write (host→device, ≤~50,000 samples/sec over USB serial) and read (device→mirror, SetSampleRate, default 22,000/sec, up to 50,000 claimed). Plus a failure mode none of the software projects have to reason about at all — too few points at too high a rate excites the MEMS mirror's own mechanical resonance and rings, a physical problem no dwell/interpolation algorithm would catch, because the cause isn't in the signal.
For reactoscope

reactoscope has the least kpps-awareness here despite being the only live, real-time system in the group. If real laser output becomes a goal, DacCapabilities{pps_min, pps_max, max_points_per_chunk} is the cleanest shape to validate against — coordBufferSize × scanFrequency is exactly the "requested pps" that config takes. Cheaper first step available today: just surface that product as a computed kpps readout in the UI and flag it past a realistic ceiling (~60 kpps) — no new dependency needed yet.

Other differences worth knowing

Persistence/phosphor

reactoscope and xyscope.js share the same accumulate→fade→blur-bloom pipeline. vectorsynthesis and laser-dac-rs have none — that's the physical phosphor/hardware's job. LaserBoy's preview has none either (a raster snapshot, not a simulation).

Color source

reactoscope reads real per-vertex RGB from geometry. Both PD/JS references derive color from a single global parameter instead (hue slider / rotating phase function).

Render/synth coupling

reactoscope owns both ends (generate + render). vectorsynthesis and xyscope.js each assume the opposite. laser-dac-rs and PlayzerX both add a third position: pure delivery middleware, owning neither — PlayzerX is that position stripped to just the wire and a buffer-depth counter.

Live vs. offline authoring

reactoscope's live DAW has no counterpart in vectorsynthesis, xyscope.js, or LaserBoy. laser-dac-rs's Frame API — "zero-copy latest-wins" submission — is structurally the closest match to reactoscope's own live-replace pattern, arrived at independently. PlayzerX has no authoring loop at all, live or offline — it's a hardware SDK, not an app.

Optimization: pipeline stage vs. menu command

reactoscope's ordering/resampling run unconditionally every frame. laser-dac-rs's transition blanking is equally unconditional, for the same reason: every frame it accepts is headed for real hardware. LaserBoy's equivalents are opt-in menu commands, except its own hardware-facing .wav path. PlayzerX has no optimization stage of any kind, ever.
